## 1. 이번 단계의 목적

오븐 전용 프로그램이 아니라 제품마다 서로 다른 프로필을 공통으로 해석하는 기반을 만든다. 계정 연결 전에도 잘못된 제어를 걸러내는 로직을 검증할 수 있도록 합성 제품을 사용했다.

공식 SDK에서 `mode`의 `r`/`w`와 `value.w`로 읽기·쓰기 및 허용 값을 구분하는 것을 확인했다. 이 구조를 참고했지만 SDK 코드를 복사하거나 설치하지 않았고, 이 단계에서 실제 API 통신도 하지 않는다.

## 3. 프로필 해석 방식

`property`와 `extensionProperty` 아래를 순회한다. 속성의 자료형, 읽기 가능 여부, 쓰기 가능 여부, 쓰기에 허용된 값을 `Capability`로 정리한다.

- enum: 지정된 값과 자료형이 일치하는 경우만 허용한다.
- range: 최소/최대/간격이 모두 유효해야 한다. Decimal로 소수 간격을 검증한다.
- boolean: 허용된 true/false 목록이 명시된 경우만 허용한다.
- 명시적 쓰기 권한이 없으면 제어 불가로 처리한다.
- 모르는 형식 또는 제약 정보가 부족한 쓰기 항목은 조회용으로만 남긴다.

이는 전체 ThinQ 스키마를 구현한 파서가 아니다. 배열/문자열/vendorObject 등 추가 쓰기 형식은 PHASE 2 실기 프로필 확인 후 확장한다. boolean 허용값 누락 시에도 보수적으로 차단하며, 실기 SDK의 해당 모델 규칙을 확인하기 전에는 자동 보정하지 않는다.

### 배열·구역·단위 보존

동일 이름의 온도 설정이 오븐 상단/하단에 각각 존재할 수 있다. 키를 단순히 `targetTemperature`로 만들면 둘이 충돌한다. 그래서 `/property/0/temperature/0/targetTemperature`와 같은 JSON pointer를 사용하고 `location`, `unit`의 문맥도 함께 보존한다.

이 키는 내부 식별자이며 **LG 제어 API에 그대로 전송하는 payload가 아니다.** 실제 요청은 제품별 어댑터가 구성해야 한다. 예를 들어 오븐은 모드·목표 온도·시작 명령을 결합하는 규칙이 있을 수 있다.

## 4. 서비스 분리

`DeviceCatalog` Protocol에 목록, 프로필, 상태 조회의 최소 인터페이스를 정의했다. 현재 구현은 `MockCatalog`이며 PHASE 2에서 공식 SDK를 감싼 조회 어댑터를 추가할 수 있다. 현재 인터페이스는 동기식이므로 비동기 SDK를 연결할 때 서버 수명주기와 async 경계를 별도로 설계해야 한다.

프로필 해석 로직은 제품 종류를 기준으로 if/else를 나누지 않는다. 새 제품 종류라도 지원되는 프로필 형식이면 해석할 수 있다. 지원하지 않는 스키마는 원본 확인과 경고로 남긴다. 이것이 모든 실물 모델 제어를 보장하는 것은 아니다.

## 5. 명령 처리 흐름

1. 제품 ID를 조회하고 온라인 여부를 확인한다.
2. 최신 모의 프로필에서 항목을 찾아 쓰기 권한과 값의 범위를 검증한다.
3. `MockIntent`를 생성한다. 준비만으로 상태가 바뀌지는 않는다.
4. 모의 적용 시 다시 검증하고 상태 revision을 비교한다.
5. 메모리의 해당 값만 갱신하고 `real_device_command_sent: false`를 반환한다.

revision이 지난 명령은 거부한다. 모의 값 변경은 물리 시뮬레이션이 아니다. 예를 들어 세탁기의 STOP 명령을 넣었다고 실제 회전·운전 상태 전이를 흉내 내지는 않는다. 프로세스가 종료되면 상태는 초기화된다.

## 8. 다음 단계에 필요한 것

실제 ThinQ 계정에 등록된 제품, 계정 국가 코드, 해당 계정의 PAT가 필요하다. PAT는 채팅/README에 붙이지 않고 이후 로컬 서버 환경설정으로만 입력한다. 먼저 조회부터 검증하며, 실제 제어는 PHASE 4에서 진행한다.

## 10. PAT 없이 진행할 수 있는 범위 — 추가 확인

확인일: 2026-11-17. **PAT 없이 프로그램 개발은 계속할 수 있지만, 현재 선택한 PAT 인증 방식에서 실제 계정·제품 연동 검증은 할 수 없다.**

| 작업 | 실제 PAT 필요 여부 |
|---|---|
| PHASE 1 모의 프로필 해석·검증·시연 | 불필요. 완료 |
| 웹 UI, 서버 구조, 명령 확인 화면 | 불필요. 모의 데이터로 개발 가능 |
| 공식 SDK 호출 코드와 인증 입력 구조 작성 | 코드 작성에는 불필요. 실제 요청 성공 확인에는 필요 |
| 실제 계정의 제품 목록·프로필·현재 상태 조회 | 필요 |
| 대상 모델의 실제 쓰기 지원과 원격 제어 조건 검증 | 실제 연동에 필요 |
| 명령 전송 및 실제 가전 상태 변화 확인 | 필요. PAT 외에도 지원 제품·연결·권한·상태 조건 충족 필요 |

공식 MCP README의 Prerequisites는 PAT와 계정 국가 코드를 요구한다. 공식 Python SDK README도 PAT 발급·설정 절차를 안내한다.

- https://github.com/thinq-connect/thinqconnect-mcp#prerequisites
- https://github.com/thinq-connect/pythinqconnect#installation-and-usage

PAT가 없어도 PHASE 2의 호출 코드를 작성하고 PHASE 3의 모의 화면을 먼저 만들 수 있다. 다만 이때 PHASE 2는 '구현됨/실기 검증 대기'로 표시해야 하며 완료 기준을 충족했다고 기록하지 않는다. 이 메모는 가능 범위 설명이며 후속 PHASE 구현을 시작한 것은 아니다.

실제 프로필을 확보하지 않고 계속 개발하면 해당 모델의 지원 기능·쓰기 값·조합 명령에 대한 가정이 남아 나중에 어댑터를 수정할 수 있다. PAT만 마지막에 넣으면 무조건 모든 제품이 작동한다는 보장은 없다. 제품별 지원 여부는 실기 조회와 제어로 따로 확인한다.

PAT는 소스 코드에 하드코딩할 필요가 없다. 후속 단계에서 사용자가 로컬 서버의 비공개 환경설정으로 입력하면 된다. 채팅에 토큰을 보낼 필요는 없다.
